# 多人协作版设计方案（多部门分权 + 共享盘 + 版本对齐）

> 状态：设计稿（未实现）。本文是实现时的唯一口径来源；改动请先改本文再改代码。
> 关联：`AGENTS.md` §3（配置口径）、`CHANGELOG.md`（发布记录）。

---

## 1. 目标与范围

五个使用身份、四台（或更多）电脑、一个企业共享盘：

| 身份 | 职责 |
| --- | --- |
| RA | 上传/更新 RA 信息 |
| EAMA | 上传/更新 产品类别、医保代码信息 |
| Global UDI Team | 上传/更新 UDI 团队信息 |
| Supply Chain | 做整合、导出、把结果发给 RA 数据接收人 |
| Admin | 全部权限（可代操作、可改配置与人员） |

要实现的行为：

1. 每人只能做自己那部分（导入/发布/整合/配置），其余按钮不出现、后端也拒绝。
2. 数据集中放共享盘（共享盘地址是**配置项**，不写死）。
3. 启动与整合前检查共享盘是否正常，**正常才开放操作权限**。
4. 某个部门更新数据后，**其他电脑能看到这份数据"已更新 · 待整合"**；整合后该标志消失，只显示最后整合时间。
5. **整合永远使用每张表的最新全量数据**，且这份数据可被证明（版本 + 哈希 + 行数）。
6. 邮件（上传通知、整合结果附件）**本期不做**，接口与配置先预留（见 §11）。

补充的数据可见性要求（本版新增）：

7. **RA / EAMA / UDI 只能看到自己负责的数据明细**；其他部门的数据只显示**最后更新时间**（看不到行数与内容）。
8. **Supply Chain 的界面要自动与共享盘对比**：有更新时提醒并**标明差异**；
   必须手动或自动**对齐全部数据之后**，才允许开始整合。
9. **Admin 拥有全部权限**：可见全部明细、可代操作、可改配置与人员。

不在本期：域账号强认证、多级审批、数据脱敏、Web 端、移动端。

## 2. 关键约束（决定架构）

1. **SQLite 不能放在网络盘上并发使用**。SQLite 明确不支持网络文件系统；WAL 依赖共享内存（`-shm`），在 SMB/NFS 上锁不可靠，多个客户端同时写有**损坏数据库**的风险。
   → 因此：**本地库继续留在各自电脑**；共享盘只放"已发布的数据快照 + 协作状态 + 结果文件"。
2. **所有使用者都能读写同一个共享盘**（公司域内、大家都有权限）。
   → 所以"部门隔离"**不能依赖共享盘 ACL**，只能由程序做（权限矩阵 + 审计）。这是**防误操作**，不是安全隔离（见 §5.3）。
3. **身份是声明式的**：登录时选择，除 Admin 外无密码；只记录**本机用户名**（不读域信息）。
4. **没有"就绪"概念**：整合不要求四份数据同时更新，每次取各来源"当前最新已发布版本"。
5. **网络盘上不能做文件监听**（不可靠）→ 状态感知用**轮询 + 手动刷新**。
6. **SC 的整合跑在"已对齐的本地数据"上**：对齐（sync）负责"拉取 + 三重校验 + 覆盖导入"，
   整合只负责"确认已对齐 + 钉住版本 + 跑本地库"。这样整合期间不依赖网络，同时保证
   导出的就是共享盘上那个版本。

## 3. 架构总览

```
        \\corp\ssr\   （共享盘；地址见 workflow.yaml 的 share.root）
┌───────────────────────────────────────────────────────────────────┐
│ published/ra/      <version>.csv + <version>.manifest.json         │
│                    原始 xlsx（审计留档）                            │
│ published/eama/    产品类别 + 医保代码（同一版本两个文件）          │
│ published/udi/                                                      │
│ state/state.json       各来源当前版本 + 最后一次整合的版本（核心）  │
│ state/state.lock       短临界区（发布/整合写状态时用）              │
│ state/consolidate.lock 整合互斥（owner / 心跳 / TTL）               │
│ consolidated/<id>/     整合结果 xlsx + summary.json                 │
│ audit/YYYY-MM-DD.jsonl 事件流                                        │
└───────────────────────────────────────────────────────────────────┘
    ▲ 发布：写自己目录 + 更新 state          ▲ 读全部 + 写 consolidated/
RA / EAMA / UDI 电脑                     Supply Chain 电脑（本地库）
（本地 SQLite，导入即发布）               Admin 电脑（全权限，可代操作）
```

- **本地库**是各自的工作副本：负责导入、校验、单份数据回顾。
- **共享盘是唯一的事实来源**：整合只读共享盘快照，绝不读别人或自己机器上的旧库。
- 每台电脑的 `config/workflow.yaml` 里配置 `share.root`（UNC 路径优先，见 §14）。

## 4. 共享盘目录与文件格式

### 4.1 版本命名

```
<版本号> = YYYYMMDDTHHMMSS-<内容 sha256 前 8 位>
例：20261031T210312-ab12cd34
```

同一来源的版本单调递增（时间戳），内容相同则哈希相同（可用作"无变化"判断）。

### 4.2 发布物结构

```
published/ra/20261031T210312-ab12cd34.csv         # 全量、UTF-8、首行列名（db_field）
published/ra/20261031T210312-ab12cd34.manifest.json
published/ra/20261031T210312-ab12cd34.xlsx        # 当时上传的原始文件（留档）
```

`manifest.json`：

```json
{
  "source": "ra_input",
  "version": "20261031T210312-ab12cd34",
  "format": "csv",
  "columns": ["material_code", "product_name", "..."],
  "rows": 31551,
  "cleaned_rows": 9562,
  "sha256": "…（csv 文件内容的哈希）",
  "content_hash": "…（可选：按行排序后的整表哈希，用于发现"行数相同但内容被换"）",
  "app_version": "2.3.13",
  "published_by": { "name": "张三", "role": "ra", "username": "zhangsan", "machine": "PC-RA-01" },
  "published_at": "2026-10-31 21:03:12"
}
```

### 4.3 `state/state.json`

```json
{
  "generation": 42,
  "sources": {
    "ra_input": {
      "version": "20261031T210312-ab12cd34",
      "sha256": "…",
      "rows": 31551,
      "cleaned_rows": 9562,
      "published_at": "2026-10-31 21:03:12",
      "published_by": { "name": "张三", "role": "ra", "username": "zhangsan", "machine": "PC-RA-01" }
    },
    "product_category": { "…": "…" },
    "medical_insurance_code": { "…": "…" },
    "global_udi_input": { "…": "…" }
  },
  "last_consolidation": {
    "id": "20261031T212044-ff00aa11",
    "at": "2026-10-31 21:20:44",
    "by": { "name": "李四", "role": "supply_chain", "username": "lisi", "machine": "PC-SC-01" },
    "versions": {
      "ra_input": "20261031T210312-ab12cd34",
      "product_category": "…",
      "medical_insurance_code": "…",
      "global_udi_input": "…"
    },
    "result": "consolidated/20261031T212044-ff00aa11/SingleSource-DCF_Column-China-UDI_20261031_212044.xlsx",
    "counts": { "ready": 2431, "missing": 7297, "duplicate": 4, "conflict": 1 },
    "gate": { "passed": true, "checks": ["versions_present", "sha256_ok", "rows_ok", "no_conflict"] },
    "email": { "status": "disabled", "recipients": [], "at": null }
  },
  "consolidation_running": null
}
```

- `generation` 每次状态变更 +1，用于"整合期间有没有人发布"的判断。
- `last_consolidation.email.status` 本期固定为 `disabled`（邮件未实现，§11）。

### 4.4 锁文件

```
state/state.lock          O_CREAT|O_EXCL 创建；内容 {"owner","machine","pid","at"}；TTL 10 秒
state/consolidate.lock    内容 {"id","owner","machine","pid","since","heartbeat"}；
                          心跳每 30 秒；TTL 30 分钟；过期可回收（写审计）
```

## 5. 身份与登录

### 5.1 启动流程

```
启动 → 登录页：
         顶部 Welcome, <本机用户名>
         上面一行四个方块（图标 + 组别）：RA / EAMA / Global UDI Team / Supply Chain
         下面一行居中一个方块：管理员（点它才出现密码框）
         点非 Admin 组别 → 直接进入；点 Admin → 输入密码
     → 记录：组别（角色）/ 本机用户名（USERNAME）/ 机器名 / 时间
     → 共享盘健康检查（§6）
     → 健康：按角色开放操作；不健康：只读 + 顶部红条 + 「重新检查」
     → 主界面
```

- **登录按组别，不按人名**：界面上不列具体人员，只显示组别方块；"登录人"= 本机用户名（`Welcome, XXX`），
  审计里记的就是这个用户名 + 组别。
- `config/users.yaml` 的作用变为：**多用户模式开关**（有它才显示登录页）+
  人员与邮箱名册（P7 邮件用）；单机模式仍然不需要它。

- **不读域信息**：只用 `os.Getenv("USERNAME")`（或 `os/user.Current().Username`），仅作记录与审计。
- 除 Admin 外**无密码**。
- **Admin 密码写死在程序里**：源码常量存 PBKDF2-HMAC-SHA256 哈希（不存明文），界面不可修改；改密码必须发新版本。
  当前密码由项目负责人保管；实现见 `internal/auth/auth.go` 的 `adminPasswordRecord`（P1 交付时同步告知）。
  连续 5 次失败冷却 1 分钟并写审计（防误触/暴力尝试，不视作强安全）。
- 切换身份 = 退出重进；每次进入写审计。

### 5.2 人员来源

`config/users.yaml`（Admin 维护；见 §14）：

```yaml
users:
  RA:                       # 固定组别键，大写，组别即角色
    name: "张三"
    email: "zhangsan@corp.com"
    note: "RA 组"
  SUPPLY CHAIN:
    name: "李四"
    email: "lisi@corp.com"
```

### 5.3 安全边界（写进用户手册）

- 身份是**声明式**的（选谁就是谁；用户名只记录、不校验），用于**划分职责、防误操作**。
- 共享盘对全员可写，程序无法阻止有人绕过程序直接改共享盘文件；
  → 所有发布物带 **sha256**，整合前校验，**手工替换会被发现并中止**（§7.4）。
- 后续可选加固：按部门收紧 `published/<部门>/` 的 ACL、共享盘上的文件签名。

## 6. 共享盘健康检查与操作权限闸门

### 6.1 检查项

| 检查 | 方法 | 超时 |
| --- | --- | --- |
| 路径可达 | 读 `share.root/state/state.json`（不存在也算可达） | 5s |
| 目录结构 | `published/{ra,eama,udi}`、`state`、`consolidated`、`audit` 存在（缺则尝试创建） | 5s |
| 可写 | 在 `state/` 写 `probe-<machine>-<ts>.tmp` → rename → 删除 | 5s |
| 锁可用 | 独占创建 `state/state.lock` 并释放 | 5s |
| 时钟偏差 | 探针文件时间与本机时间差 > 5 分钟则告警（影响"新旧"判断） | — |
| 整合锁 | 读 `consolidate.lock`：有人在整合 / 心跳是否新鲜 / 是否过期可回收 | — |

### 6.2 时机

- **启动时**（完成身份选择之后）；
- **每次发布前**（避免"以为传上去了"）；
- **每次整合前**（用户明确要求的那一步）。

### 6.3 状态机

```
checking ──成功──→ ready（按角色开放写操作）
   └────失败──→ locked（只读；顶部红条写明原因；「重新检查」按钮）
```

`locked` 时：导入/发布/整合/改配置/改人员全部置灰；仍可查看本地已有结果与日志。

### 6.4 共享盘地址

`config/workflow.yaml` 的 `share.root`：

```yaml
share:
  root: '\\\\corp\\ssr'      # UNC 优先；也允许本地绝对路径（测试用）
```

- 部署：`share.root` 根目录由 IT 预置；第一次检查通过后程序自动补齐
  `published/{ra,eama,udi}`、`state`、`consolidated`、`audit`，其余文件按首次使用生成
  （`state.json`/版本文件/`consolidated/<id>/`/`log/`）。
- 「参数设定 → 共享盘」页可改（Admin）：P5 已实现（编辑 `workflow.yaml`，`share.root` 留空 = 本地模式；
  保存后重开程序生效，连接状态用状态栏的「重新检查」验证）；收件人列表也在这一页签里增删。
- 操作日志（「记录导出」）所有人可见：并集写入回顾表并同步到 `<share>/log/`（P5 追加，见 `app_oplog.go`）。
- 未配置（空串）→ **本地模式**：不发布、不整合共享数据，只能导入与本地导出（保证离线可用与回归测试）。
- 每台电脑各自配置；建议部署时由安装包/管理员一次性写入。

**本地目录也能当共享盘（测试/演练必用）**：

- `share.root` 允许填**本地绝对路径**（如 `/tmp/ssr-share`、`D:\\ssr-share`），代码对本地目录与 UNC 走**同一套**
  逻辑（都是文件操作：`O_EXCL` 锁、临时文件 + `rename`、读 `state.json`）；
- 相对路径不允许（避免"各人工作目录不同"的歧义）；路径末尾的分隔符会被规整；
- 首次使用提供 **「初始化共享盘」** 动作（Admin）：建出 `published/{ra,eama,udi}`、`state`、`consolidated`、`audit`，
  写入 `state.json`（`generation: 0`，四个来源为空）与一份 `README.txt`；
  本地演练时先点一次即可，生产环境由管理员建一次或直接手工建目录；
- 本地目录**不会**出现网络盘那种"突然不可达"，要测锁定分支就把目录改名/删掉，或把 `share.root` 指向不存在的路径，
  检查「共享盘异常 → 只读锁定 → 重新检查恢复」；
- 本地目录上"时钟偏差"检查恒为通过（探针文件就在本机），属预期。

## 7. 数据对齐机制（核心）

> 目标：**整合使用的每一份数据，都能证明是"共享盘上某来源某个版本的全量内容"**；
> 任何人本地库是否最新都不影响结果。做法分两段：**对齐（sync）** 与 **整合（consolidate）**。

### 7.1 五个规则

| 规则 | 做法 | 防的是 |
| --- | --- | --- |
| **全量发布** | 发布时把当前暂存表**整张**写 CSV（不是增量），manifest 记行数/哈希；先写 `.tmp/` 再 `rename` | 半份/增量 |
| **先文件后状态** | 快照落盘成功后才在 `state.lock` 下更新 `state.json`；写 `state.json.tmp` 再 rename | 状态指向不存在的文件 |
| **对齐时才拉取** | 「对齐」= 读 `state.json` 找最新版本 → 拉取到本地临时目录 → 三重校验 → **覆盖导入**本地库 → 记 `synced_versions` | 拿旧数据整合 |
| **整合前校验已对齐** | 整合开始前比较 `state.sources[s].version` 与本地 `synced_versions[s]`；不一致→**禁止整合** | 对齐后又被别人更新 |
| **钉住版本** | 对齐通过后记录四个版本；整合全程只读本地库 | 跑的过程中数据被换 |

`synced_versions` 是本地记录的"本机当前已导入哪一版"（来源 / 版本 / sha256 / 行数 / 对齐时间 / 对齐人），
用于界面显示"本地版本 vs 共享盘版本"的差异。

> 实现进度：P2 已落地"全量发布 + state.json + state.lock + 导入前闸门"；
> **P3 已落地对齐（sync = 拉取 + sha256/行数校验 + 整表覆盖导入 + `synced_versions`）**、
> 按角色的可见性（RA/EAMA/UDI 只看自己明细，其他来源只给最后更新时间）、
> 「已更新 · 待整合」徽标与最后整合时间、以及"未对齐禁止整合"。

### 7.2 对齐（sync）时序

```
1. 共享盘健康检查（§6）
2. 读 state.json → 得到四个来源的 version（+ sha256、行数、发布人、时间）
3. 与本机 synced_versions 比较 → 得出"需要对齐的来源"清单（差异也就是界面要标明的）
4. 逐份：拉取到本地 tmp/ → 校验 sha256 与行数（可选列头/键数）
     不符 → 中止该来源，报"版本损坏，请该部门重新发布"（不降级用旧版）
5. 覆盖导入本地库（replace_on_import）→ 写 synced_versions
6. 写审计（对齐了哪些来源、从哪个版本到哪个版本）
```

### 7.3 整合（consolidate）时序

```
1. 共享盘健康复查 → 失败即中止
2. 对齐校验：share versions == synced_versions；不一致 → 禁止整合，列出差异（§10）
3. 取 consolidate.lock → 钉住四个版本 → 写 consolidation_running
4. 跑本地库（已对齐）→ 门禁 → 导出到 consolidated/<id>/ + summary.json（含四个版本）
5. 写 state.last_consolidation（版本/计数/文件/操作人/时间）
6. 再读 state：generation 变了 → 该来源显示"共享盘有更新"，需要再次对齐+整合
7. 释放锁 → 审计 → 通知（邮件未实现时 no-op，§11）
```

### 7.4 对齐不变量（可判定、可显示）

```
已对齐  ⇔ synced_versions[s].version == state.sources[s].version          （SC 才能整合）
已更新  ⇔ state.sources[s].version   != last_consolidation.versions[s]     （所有人可见的"待整合"）
```

- RA/EAMA/UDI 只对自己那份看"已更新/已整合"；SC 与 Admin 看全部。
- 对齐后若又有人发布：SC 界面立刻显示"共享盘有更新"，`开始整合` 重新置灰，直到再次对齐。

### 7.5 三重校验

| 校验 | 时机 | 不一致 |
| --- | --- | --- |
| sha256 | 拉取后对比 manifest | 中止该份对齐 |
| 行数 | 导入后对比 `manifest.rows`（RA 另比 `cleaned_rows`） | 中止 |
| 列头 / 关键键数 | 导入后对比 manifest 的列与 `material_code` 去重数（可选加强） | 中止 |

结果自证：`summary.json`、导出文件名、审计都写明本次使用的四个版本。

### 7.6 失败与并发矩阵

| 场景 | 结果 |
| --- | --- |
| 发布时断网 | 发布失败并提示；共享盘无半份文件、状态不变 |
| 两人同时发布（不同来源） | `state.lock` 串行化，两份版本都记上，不丢更新 |
| 发布写文件中，SC 在对齐/整合 | 状态在 rename 后才更新；sha256 兜底；对齐中的那份按旧版本完成，随后显示"有更新" |
| 对齐中途有人发布 | 已对齐完成的来源记 synced；新版本让该来源再次显示"有更新" |
| 整合中途有人发布 | 本次用钉住版本完成；新版本显示"有更新"，需再次对齐+整合 |
| 快照被手工改过 | sha256 不符 → 中止对齐，报"版本损坏" |
| 两个 SC 同时整合 | `consolidate.lock` 只放行一个，另一个看到"谁正在整合" |
| 某来源从未发布 | 无法对齐 → 禁止整合，报"XX 还没有发布数据" |
| 本地库是旧的 | 未对齐时禁止整合；对齐时整表覆盖导入 |

### 7.7 可选加强

1. `content_hash`（整表内容哈希）比对；
2. 整合期间新版本策略（配置）：`warn`（默认）/ `auto_rerun`（最多重跑一次）/ `block`；
3. 保留最近 N 个版本，支持"用上一版重跑/对比"；
4. 同部门多人：后发布者覆盖（旧文件留档）；SC 若检测到"本机落后于共享盘"会提示先对齐，避免用旧数据覆盖别人的发布。

## 8. 状态、可见性与「待整合」标志

### 8.1 每类角色能看到什么

| 可见项 | RA / EAMA / UDI | Supply Chain | Admin |
| --- | --- | --- | --- |
| **自己负责的来源明细**（原文 / 清洗后） | ✅ | ✅（只读） | ✅ |
| **其他来源明细** | ❌ | ✅（只读） | ✅ |
| **其他来源的最后更新时间** | ✅（只有时间） | ✅ | ✅ |
| 自己来源的版本 / 已更新·待整合 / 最后整合时间 | ✅ | ✅ | ✅ |
| 四份数据"本地 vs 共享盘"的对齐状态与差异清单 | ❌ | ✅ | ✅ |
| 最后整合时间 + 操作人 | ✅ | ✅ | ✅ |
| 审计（自己 / 全部） | 自己 | 全部 | 全部 |

- 后端统一裁决：请求"看别人明细"直接拒绝（不是只把入口藏起来）。
- 其他来源那一行只显示 **「最后更新：2026-10-31 21:03」**，不显示行数、内容与发布人。

### 8.2 状态推导

```
已对齐  ⇔ synced_versions[s].version == state.sources[s].version       （仅 SC/Admin 用）
已更新  ⇔ state.sources[s].version   != last_consolidation.versions[s]  （所有人，按 §8.1 范围）
```

- 上传后：该来源显示 **「已更新 · 待整合」**（自己看得到；SC/Admin 看全部；其他人只看到时间）。
- 整合后：标志消失；所有人看到 **「最后整合：时间 + 操作人」**。
- 没有"就绪"：整合不要求四份同时更新。

### 8.3 Supply Chain 的对齐面板

界面固定显示四行（来源 / 本机版本 / 共享盘版本 / 差异）：

```
RA 信息        本机 20261031T2103-ab12cd34   共享盘 20261031T2130-77aa11bb
               ⚠ 有更新：2026-10-31 21:30 由张三发布（31,551 → 31,602 行）
产品类别       本机 20261030T0900-11bb22cc   共享盘 20261030T0900-11bb22cc   ✓ 已对齐
医保代码信息   …
UDI 团队信息   …
[ 立即对齐 ]  [ 全部对齐 ]  自动对齐：开
[ 开始整合 ]（未对齐时置灰，并写明"还有 2 份数据未对齐：RA、UDI"）
```

- **自动对比**：每 30 秒（可配）读一次 `state.json`，发现落后就提示，并自动刷新差异清单。
- **刷新方式**：手动点「立即对齐/全部对齐」，或开启「自动对齐」（默认开；可在参数设定关闭）。
- **整合门禁**：全部对齐才解锁「开始整合」；整合进行中禁用对齐与再次整合。
- 差异粒度：**版本级**（谁、何时、行数变化）+ 需要时展开为"本批新增/消失的规格型号数"；
  逐行 diff 不在本期（可后续加）。

## 9. 上传 / 发布流程

```
选文件 → 导入校验（现有规则，含 RA 清洗）→ 写本地库
→ 共享盘健康复查 → 发布：写 published/<部门>/<version>.csv + manifest + 原始 xlsx（原子）
→ state.lock 内读改写 state.json（该来源版本/发布人/时间/generation+1）
→ 释放 → 写审计 → 通知钩子（§11，本期 no-op）
```

- 发布失败必须明确报错（不能"看着成功"）。
- 同一来源重复发布：新版本覆盖为"当前"，旧文件保留。

## 10. 整合流程（先对齐，后整合）

- **没有就绪概念**：不要求四份在同一批次都更新；每个来源取 `state.sources[s].version`。
- **前置条件**：
  1. 共享盘健康（§6）；
  2. 四份数据**全部已对齐**（`synced_versions` == `state.sources`）；
  3. 每个来源至少发布过一次。
  任一不满足 → 「开始整合」置灰并写明原因（缺哪份、落后多少）。
- 对齐后如果又有人发布 → 立刻回到"未对齐"，必须先对齐。
- 四个版本与上次 `last_consolidation.versions` 完全相同 → 允许执行，但提示"数据无变化"
  （不重复通知；本期无邮件）。
- 门禁沿用现有口径：只导出 `Ready`；RA 清洗冲突（`clean.conflict: error`）直接中止并提示。
- 结果落 `consolidated/<id>/`，并在 `state` 记录四个版本（可追溯到"这封邮件/这份文件用了哪一版"）。

| 文件 | 内容 | 可改者 |
| --- | --- | --- |
| `config/workflow.yaml`（新） | `share.root`（**共享盘地址，配置项**）、轮询间隔、门禁口径、整合期间新版本策略、`recipients.*` 与 `email.*`（占位） | Admin |

`workflow.yaml` 样例：

```yaml
share:
  root: '\\\\corp\\ssr'        # 空串 = 本地模式（不发布/不整合共享数据）
  poll_seconds: 30
  probe_timeout_seconds: 5
  consolidate_lock_ttl_minutes: 30
sync:
  poll_seconds: 30                 # 自动对比共享盘的间隔
  auto: true                       # 自动对齐（参数设定里可关）
  require_before_consolidate: true # 未对齐禁止整合
consolidation:
  on_new_version_during_run: warn   # warn | auto_rerun | block
  skip_unchanged: true
recipients:                        # 邮件未启用，先放配置
  ra_receivers: []
  supply_chain: []
  admins: []
email:
  transport: disabled              # disabled | smtp | graph | outbox
```

**兼容策略**：

- 没有 `users.yaml` → **单机模式**：全权限、行为与现在一致（发布流水线回归依赖它）。
- `share.root` 为空 → **本地模式**：可导入、可本地整合导出，不做发布与共享盘检查。
- 没有 `workflow.yaml` → 按 `share.root` 为空处理。

| 类别 | 用例 |

| 并发 | 两个部门同时发布不丢更新；两个 SC 同时整合只放行一个 |

| 故障模拟 | `share.root` 指向不存在/被改名/只读目录 → 启动即锁定；恢复后「重新检查」解锁 |

3. 整合期间出现新版本的默认策略（warn / auto_rerun / block）。
4. 历史版本保留数量与清理规则。
5. 邮件：通道、发件人、RA 收件人、SC/Admin 地址、附件大小与 DLP 要求（决定 P7）。
6. 是否允许同一部门多人（后发布覆盖）以及是否需要双人核对。
7. SC 的「自动对齐」默认开还是关（本版默认开，见 §20）。
8. 差异粒度：版本级（谁/何时/行数变化）是否够用，是否需要"本批新增/消失的规格型号数"。

## 19. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 网络盘上放 SQLite 损坏 | 不这么做：库留本机，共享盘只放快照与状态 |
| 身份声明式、全员可写共享盘 | 明确"职责划分而非安全隔离"；sha256 校验防替换；审计留痕；后续可收紧 ACL |
| 网络盘瞬时不可用 | 启动/发布/整合三处健康检查；失败即锁；原子写 |
| 并发发布/整合 | `state.lock` 短临界区 + `consolidate.lock` 心跳/TTL |
| 用旧数据整合 | 版本钉住 + 三重校验 + 徽标 + 结果记录四个版本 |
| 邮件（后续）被 DLP 拦 | outbox 兜底、附件大小检查、上线前与 IT 验证 |
| 硬编码 Admin 密码泄露 | 存哈希常量；泄露只能发新版；失败冷却 + 审计 |

## 20. 本版默认口径（如无异议按此实现）

| 项 | 默认口径 | 说明 |
| --- | --- | --- |
| 部门可见范围 | RA/EAMA/UDI 只看**自己来源明细**；他人来源只显示**最后更新时间**（不含行数/发布人） | 后端拒绝越权读取，不只是隐藏入口 |
| 自己数据的整合状态 | 自己那份显示"已更新·待整合 / 已整合"；最后整合时间所有人可见 | 便于上传方确认"我这份被整合了没有" |
| SC 的对比与对齐 | 每 30 秒自动对比共享盘；**自动对齐默认开**；未对齐禁止整合；整合中禁用对齐 | 可在参数设定关闭自动对齐 |
| 差异展示 | 版本级（来源、旧→新版本、发布人、时间、行数变化）；可选展开"新增/消失的规格型号数" | 逐行 diff 本期不做 |
| 整合数据来源 | 本机**已对齐**的库（覆盖导入后的整表），整合前校验并钉住四个版本 | 保证"导出的就是共享盘那一版" |
| 身份 | **按组别选择**（四个方块 + 管理员一个方块，显示 Welcome, 本机用户名）；Admin 密码写死在程序里 | 职责划分，不是安全隔离 |
| 共享盘地址 | `workflow.yaml` 的 `share.root`（配置项，可在参数设定修改并"测试连接"） | 支持 UNC 或**本地绝对路径**（本地目录用于测试/演练）；空串 = 本地模式 |
| 邮件 | 本期只留接口与配置位，不发送（P7 再实现） | 交付替代：结果文件 + 打开所在文件夹 |
| 无就绪概念 | 整合取每个来源的当前最新版本，不要求四份同时更新 | 首次上线需各发布一次 |
