# 现状（Python + PySide6）vs 新实现（Go + Wails v2）对比报告

依据 AGENTS.md §9.2（数据口径① + 文件口径②）、§9.3（golden baseline）、§11.5（性能口径）。
所有数字都是本机实测（macOS / Apple Silicon，1800×1169 逻辑分辨率），环境见
`ssr_go/perf-baseline/性能基线.json`。

## 1. 导出文件与行为：逐格 diff = 0

用 Python 现状实现产出的 `ssr_go/baseline/` 作对照物，Go 侧用
`ssr-core snapshot` 产出同名的快照后逐字节比较：

| 快照 | 结果 |
| --- | --- |
| `来源表_ra_input.tsv`、`来源表_global_udi_input.tsv`、`来源表_medical_insurance_code.tsv`、`来源表_product_category.tsv` | **逐字节一致** |
| `整合结果.tsv`（status + 30 导出列 + material_code，9 行） | **逐字节一致** |
| `计数断言.json`（Ready 8 / Incomplete 1 / Duplicate 0 / Conflict 0、缺失行 `000MAT-006::MISSING`） | **逐字节一致** |
| `导出文件_逐格.tsv`（导出 Excel 数据区逐格文本，220 个单元格） | **逐字节一致** |
| `操作日志.json`（operation_log 归一化，8 条） | **逐字节一致** |
| `幂等路径.json`（再整合全部 Duplicate、不新增日志、报错原文） | **逐字节一致** |
| `变更路径.json`（改字段 → `Product Name/Generic Name changed`；改医保编码 → 同一身份 + `Medical Insurance Code changed`） | **逐字节一致** |
| `拒绝路径.json` / `.txt`（UDI 文件被拒，行号 13/14 与命中条件逐字） | **逐字节一致** |
| `导出文件_部件清单.tsv` | **有意不同**，见下一节（口径②） |

即：**12 个行为快照逐字节一致**，唯一差异是模板保真度——这正是拍板采纳的改进。

## 2. 导出文件的 zip 部件清单（§9.1 的重跑）

模板共 38 个部件；导出后：

| | 丢失 | 原样保留 | 保留但大小变化 |
| --- | --- | --- | --- |
| 现状（openpyxl） | **24** | 1 | 13 |
| 新实现（excelize） | **0** | 30 | 8 |

现状丢掉的 24 个部件是：`docMetadata/LabelInfo.xml`（**敏感度标签**）、`xl/media/image1.png`、
`xl/media/image2.png`、3 个 `xl/drawings/*` 及其 rels、3 个 `xl/printerSettings/*.bin`、
9 个 `customXml/*`、`xl/sharedStrings.xml` 与两个 sheet rels。新实现把它们**全部保留**
（个别部件因 excelize 重写共享字符串表而大小变化，但内容与结构都在）。

## 3. 性能

### 3.1 体积

| | 现状 | 新实现 |
| --- | --- | --- |
| 运行时 | venv **1.3 GB**（PySide6 约 1.2 GB） | 无需运行时 |
| 单一产物 | 发布目录约 1.2 GB（`onedir`） | `.app` **16 MB**（可执行文件 15.5 MB）；`ssr-core` CLI 16.5 MB |

### 3.2 端到端（4 份样本导入 → 整合 → 导出 → 三条场景路径）

| | 现状（`scripts/snapshot_baseline.py --no-perf`，含 openpyxl 生成样本） | 新实现（`ssr-core snapshot`，读现成样本） |
| --- | --- | --- |
| 3 次实测 | 4.719 / 3.907 / 3.884 s | 0.295 / 0.149 / 0.147 s |
| 中位数 | 3.907 s | **0.149 s** |

⚠ 两者包含的工作不同（现状那一侧还要用 openpyxl 生成 8 份样本工作簿），所以这不是纯等价比
较；但 §8.2 的目标「样本端到端 ≤ 现状 × 1.5」显然是满足的。

### 3.3 单进程启动与内存

| | 现状 | 新实现 |
| --- | --- | --- |
| 启动到可用 | `import ui.main_window` 612 ms（完整启动更长） | CLI 热启动 **0.02 s**（首次冷启动 1.17 s，含页面缓存未命中） |
| 进程峰值 RSS | 186 MB（Python 单进程口径） | 桌面版是 Wails 主进程 + 系统 WebView 辅助进程，**必须按所有相关进程 RSS 之和**测量（§11.5），本报告尚未测 |

GUI 冷启动与内存的正式测量（5 次中位数、清缓存后冷启动）还**没有做**，属于待补项。

## 5. 已知差异清单（§11.6）

| # | 差异 | 影响 | 处置 |
| --- | --- | --- | --- |
| 1 | 导出文件保留模板部件（含敏感度标签、图片、打印设置） | 导出文件比现状更接近模板原貌 | **已拍板采纳**（§10.1 #2，质量提升） |
| 2 | 单元格里**真实的日期/数字**渲染：现状是 openpyxl + pandas，新实现是 excelize | 当前样本里日期都是文本，未被 golden diff 覆盖；用户若在输入里用真正的日期单元格，两边渲染可能不同 | **待确认**：需要一批含真实日期单元格的输入做对照 |
| 3 | 列声明类型：现状 SQLAlchemy 写 `VARCHAR`，新实现写 `TEXT` | SQLite 里两者都是 TEXT 亲和性，读写行为一致；只有 `PRAGMA table_info` 的声明类型不同 | 记录在案；`alignlogcolumns` 用 `TEXT` 与运行时一致 |
| 4 | `config/log_columns.yaml` 生成物的注释里保留了 Python 的示例命令 | 纯注释 | 有意为之：两个仓库的 `config/` 保持逐字节一致 |
| 5 | 医保编码来源的「…」数据回顾按钮 | 现状渲染时被注释掉（导入后仍禁用），新实现可用 | **已拍板修好**（§10.1 #3） |
| 6 | 菜单在 macOS 上的表现 | 现状（Qt）与 Wails 的菜单都由系统呈现；Wails 需要显式补一个系统应用菜单，「文件」才会独立出现 | 已修，见提交 `4b18a75` |
| 7 | 界面像素级尺寸（如集成布局断言） | 现状有一条用例断言窗口 962 高时导入区高度等于 sizeHint；Wails/WebView 的排版由 CSS 决定，不保证逐像素相同 | 以「结构、文案、状态、文案级行为」为准（§6），不追求像素一致 |

## 6. 尚未完成的验收
